# ADR 004: NNG + FlatBuffers for Inter-Process RPC and PubSub

**Date**: 2026-05-22 (inferred from codebase)

## Context

The bitcoind-nng crate communicates with a custom bitcoind node via an inter-process protocol. The protocol needs:
- Synchronous RPC for querying blocks, mempool, and mining templates
- Asynchronous PubSub for receiving block connect/disconnect events, mempool updates, and mining work changes
- A binary serialization format that is efficient (zero-copy deserialization) and self-describing (for forward/backward compatibility as the node evolves)

## Decision

Use NNG (nanomsg next generation) as the transport layer with FlatBuffers as the serialization format.

**Transport:**
- RPC: `Req0`/`Rep0` protocol (request-reply)
- PubSub: `Sub0`/`Pub0` protocol (publish-subscribe)
- TCP as the underlying transport

**Serialization:**
- Schema defined in `flatbuffers/nng_interface.fbs`
- Rust types generated by the `flatbuffers` crate
- RPC messages carry a union discriminant (`BlockIdentifier` = Height or Hash)
- PubSub messages carry the raw flatbuffer table, parsed based on the subscribed topic

**Configuration:**
- RPC endpoint URL and PubSub endpoint URL are passed as connection strings
- `RecvBufferSize` is set to 1024 to handle burst events (reorgs, burst blocks)
- Flatbuffer verifier limits are set with custom `VerifierOptions` (`max_tables: 0xffff_ffff`)

## Considered Options

1. **HTTP + JSON** — Simpler to debug but higher overhead, no built-in pubsub without WebSocket, no zero-copy.
2. **gRPC / protobuf** — Established standard but requires a full gRPC stack; NNG is simpler for an embedded IPC.
3. **Raw TCP + custom framing** — Maximum control but requires custom connection management, reconnection, and framing.
4. **NNG + FlatBuffers (chosen)** — Zero-copy deserialization, schema evolution via flatbuffer's union/tables, NNG handles reconnection and framing.

## Consequences

**Positive**:
- Zero-copy reads: flatbuffer data accessed directly from the wire buffer
- Schema evolution: adding fields to flatbuffer tables doesn't break old readers
- NNG handles backpressure, reconnection, and multi-protocol support
- PubSub topics are simple string subscriptions (block_connected, mining_work_changed, etc.)
- RPC and PubSub share the same schema file, ensuring consistency

**Negative**:
- FlatBuffers (v2.0) dependency has a heavyweight build: requires `flatc` compiler installation
- `flatc` compilation not reproducible via `cargo` alone; documented in build instructions
- Debugging flatbuffer messages is harder than JSON (need flatbuffer tools to inspect)
- Mutex synchronization on the RPC socket (NNG Req0 requires serialized requests)
- 1024 buffer size is a heuristic; too small for extreme reorgs, too large wastes memory on idle nodes
